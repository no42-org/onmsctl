EC007 — alarm-type out of accepted range

Rule
----
The local schema strictly accepts `alarmType` in two equivalent forms:

  Integer  Symbolic         Meaning
  -------  --------------   ----------------------------------------
     1     "raise"          raises an alarm, paired with a Resolution
                            (alarmd Java code calls this `Problem`)
     2     "resolution"     clears a paired Raise by reductionKey
     3     "unresolvable"   Raise-class with no auto-clear from the
                            device; requires manual close or an
                            alarmd cleanup policy

Anything else is rejected:

  - YAML input with an unknown symbolic string (e.g. `"problem"`,
    `"crit"`) fails at deserialize time with a `config error` naming
    the offending value.
  - YAML input with an out-of-range integer (e.g. `4`, `0`, `-1`)
    fails at deserialize time with the same error class, naming the
    bad value and the accepted set.
  - Eventconf XML with an unrecognized `alarm-type` attribute (e.g.
    `alarm-type="4"`) reaches `event-source convert` and produces an EC007
    finding at Error severity. YAML is NOT written. Exit code is 2.

Symbolic input is case-insensitive (`Raise` / `RAISE` / `raise`).
Whitespace is NOT trimmed by the deserializer — but YAML's own
scalar handling strips leading/trailing whitespace from *unquoted*
plain scalars before the deserializer sees them. So
`alarmType: raise ` (unquoted, trailing space) parses successfully;
`alarmType: "raise "` (quoted, trailing space) fails as unknown.

Why
---
Pre-stability (`v0.x.y`) the schema is intentionally narrow: known
states only. Operators get clear errors instead of silently mapping
unknown values to a placeholder.

If OpenNMS adds a new alarm type in a future release, a follow-up
schema change widens the enum. See `event-source-alarm-type-symbolic-names`
for the pattern used to add new states.

How to fix
----------
1. CONFIRM THE VALUE — check the source XML for the cited event. Is
   the value (e.g. `alarm-type="4"`) intentional, or a typo?

2. TYPO — fix the source XML. Values 1, 2, 3 cover the documented
   semantic space.

3. INTENTIONAL — file a schema-widening change to add the new state
   to `AlarmType` (variants), `from_wire`, `to_wire`, `JsonSchema`,
   the EC007 explainer, and the test surface. The
   `event-source-alarm-type-symbolic-names` change archived under
   `openspec/changes/archive/` is the reference pattern.
